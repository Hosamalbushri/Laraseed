# Phase 13 Step 02B — Optional Package Composition Report

Date: 2026-09-29  
Mode: deterministic deployment composition, no undo, no data deletion.

## 1. Outcome

PASS. CampusHub now has one validated Optional-package state. Foundation remains always composed. Student, Event, and LostAndFound remain available through Composer autoload, while their main providers and Concord modules are derived atomically from the selected deployment composition.

No marketplace, installer/downloader, database feature flag, Admin toggle, hot loader, runtime mutation, or arbitrary package discovery was introduced.

## 2. Rules and Prior Reports

Read the rules index, Rules 06–13, the Step 01 lifecycle audit, and the Step 02A decoupling report. Rule 08 remains the architectural owner and now records the permanent deployment-composition law.

## 3. Revalidated Baseline

Before Step 02B implementation: Laravel 12.61.1; PHP 8.4.24; Composer valid; 120 routes; zero scheduled tasks; 530 tests / 3,437 assertions. The Step 02A implementation and its dirty-worktree state were preserved.

Physical revalidation confirmed eight manual Optional composition references: three root PSR-4 availability mappings, three main providers, and two Concord modules. The three PSR-4 mappings remain intentionally because availability is not enablement. The five independent provider/module switches were replaced.

## 4. Authoritative Deployment Configuration

`config/campushub.php` is the one enablement source. `CAMPUSHUB_OPTIONAL_PACKAGES` feeds that config only and accepts a comma-separated set of stable IDs. The default remains `student,event,lost_and_found`; an empty value selects Foundation only.

Application code never reads the environment directly. `config:cache` compiles the selected state, catalog, dependency graph, ordered providers, and ordered Concord modules into normal Laravel configuration.

## 5. Canonical Package Metadata

The three Optional package manifests own `extra.campushub` lifecycle metadata:

| ID | Manifest | Main provider | Concord module |
| --- | --- | --- | --- |
| `student` | `packages/Webkul/Student/composer.json` | `StudentServiceProvider` | none |
| `event` | `packages/Webkul/Event/composer.json` | `EventServiceProvider` | `Event\Providers\ModuleServiceProvider` |
| `lost_and_found` | `packages/Webkul/LostAndFound/composer.json` | `LostAndFoundServiceProvider` | `LostAndFound\Providers\ModuleServiceProvider` |

The fields are limited to `id`, `type`, `provider`, and `concord_module`. Optional dependencies are not duplicated in lifecycle metadata: they are derived from each manifest's corrected Composer `require` map.

## 6. Dependency Graph

The compiled graph is:

```text
student        -> none
event          -> student
lost_and_found -> student
```

`OptionalPackageComposition` validates unknown IDs, duplicate IDs, provider/module classes, missing dependencies, cycles, and enabled dependency closure. Its topological ordering registers Student before Event and LostAndFound. Reverse dependency answers are derived from the same forward graph; with all packages enabled, Student has enabled dependents `event` and `lost_and_found` and cannot be disabled safely.

## 7. Provider and Concord Atomicity

`bootstrap/providers.php` consumes only `campushub.optional_packages.providers`; it no longer names an Optional provider. `config/concord.php` consumes only `campushub.optional_packages.concord_modules`; it no longer names an Optional module.

Both lists were generated by the same validated composition instance during configuration loading. Student is handled generically even though it has no Concord module. Foundation providers and Foundation Concord modules remain explicit and unconditional.

## 8. Failure Semantics

Invalid composition throws `Webkul\Core\Exceptions\InvalidPackageComposition` during configuration loading, before usable application boot. Verified examples include:

```text
Optional package "event" requires enabled package "student".
Optional package "lost_and_found" requires enabled package "student".
Unknown Optional package ID [studnet].
```

Failures did not degrade into class-not-found, route, binding, or SQL errors. Synthetic tests also reject duplicate IDs, missing provider/module classes, and dependency cycles.

## 14. Migration and Data Safety

No migration was created or executed. No schema, table, row, optional source file, or stored object was deleted or modified by composition work. Tests used the repository's established transactional test behavior. Disabling only removes provider-owned discovery and contributions: `DISABLE != UNINSTALL`.

## 15. Cache Verification

Configuration cache passed in both directions:

- Foundation-only cache built successfully and remained at 69 routes even when the later process environment requested all packages.
- All-enabled cache built successfully and remained at 120 routes even when the later process environment requested Foundation only.

This proves runtime reads compiled config rather than environment. Route cache also built and loaded successfully for Foundation-only (69) and all-enabled (120) compositions. As with any Laravel deployment configuration change, config and route caches must be rebuilt together; a deliberately stale route cache from a different composition is not a supported mixed state.
