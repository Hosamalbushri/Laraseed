## 1. Forensic Architecture Audit

A forensic inspection of the existing Foundation was performed across `packages/Webkul/*`:
1. **Repository Pattern:**
   - Foundation repositories (`Webkul\User\Repositories\UserRepository`, `RoleRepository`, `GroupRepository`, `Webkul\Core\Repositories\CountryRepository`, `LocaleRepository`, `Webkul\DataGrid\Repositories\SavedFilterRepository`) extend `Webkul\Core\Eloquent\Repository` (which extends Prettus `BaseRepository`).
   - Repositories specify `model(): string` returning the canonical contract string (e.g. `'Laraseed\Contacts\Contracts\Contact'`), which Concord resolves to the concrete model.
   - Foundation repositories do NOT introduce speculative individual interface contracts per repository (there is no `UserRepositoryInterface` or `CountryRepositoryInterface`).
2. **FormRequest Pattern:**
   - FormRequests live in `src/Http/Requests` and extend `Illuminate\Foundation\Http\FormRequest`, returning validation rules decoupled from UI/Admin.
3. **Transaction & Event Dispatching:**
   - Foundation operations wrap critical multi-step persistence in `Illuminate\Support\Facades\DB::transaction()`.
   - Domain events are dispatched via `Illuminate\Support\Facades\Event::dispatch()` after persistence state is ensured.
4. **Lifecycle & Delete Protection:**
   - Base entities handle data access and lifecycle transitions directly, avoiding premature coupling to downstream consumer modules.

## 5. Validation Architecture

Validation operates across two distinct boundaries:
1. **HTTP Request Boundary (FormRequests):**
   - `StoreContactRequest`: Validates HTTP input for creating contacts.
   - `UpdateContactRequest`: Validates partial HTTP input (`sometimes|required`) for updating contacts.
   - Rule summary:
     - `type`: `in:person,organization`
     - `name`, `first_name`, `middle_name`, `last_name`, `job_title`: string, max:100-255
     - `organization_name`: string, max:255
     - `tax_number`: string, max:50 (not globally unique)
     - `email`: email format, max:255 (not globally unique)
     - `country_code`: string, size:2
     - `website`: URL syntax, max:255
     - `is_active`: boolean
2. **Domain Operations Boundary (`ContactRepository`):**
   - Invariants are protected in `validateDomainInvariants(array $attributes, bool $isCreate = true)` when invoked via CLI, Seeders, Background Jobs, or APIs without depending on HTTP `FormRequest`.

## 6. Canonical Name Policy

The canonical `name` column is derived deterministically through a single centralized rule in `ContactRepository::deriveCanonicalName()`:

1. **Person (`type === 'person'`):**
   - If individual name components (`first_name`, `middle_name`, `last_name`) are supplied, canonical name is computed as:
     `trim(implode(' ', array_filter([first_name, middle_name, last_name])))`
   - If no components are provided, falls back to explicit `name`.
   - If updating and neither is changed, preserves existing `name`.
   - Otherwise, throws `InvalidArgumentException`.
2. **Organization (`type === 'organization'`):**
   - If `organization_name` is supplied, canonical name is `trim(organization_name)`.
   - If absent, falls back to explicit `name`.
   - If updating and neither is changed, preserves existing `name`.
   - Otherwise, throws `InvalidArgumentException`.

---

## 7. Normalization & Nullable Policy

Centralized in `ContactRepository::normalizeAttributes()`:
- **String Trimming:** All string fields are trimmed.
- **Empty Strings to `null`:** For all nullable attributes, `""` or whitespace-only `"   "` is converted to `null`.
- **Email:** Trimmed and converted to lowercase (`strtolower`).
- **Country Code:** Trimmed, uppercased (`strtoupper`), max 2 characters (e.g. `SA`, `US`, `AE`).
- **Phone / Mobile:** Trimmed without stripping `+` or destructive masking.
- **Boolean Status:** Converted to native PHP boolean (`(bool) $val`).

---

## 8. Type Transition Policy

When updating a contact with a type transition:
1. **`person` → `organization`:**
   - Person-specific fields (`first_name`, `middle_name`, `last_name`, `job_title`) are automatically set to `null` to avoid leaving stale identity residue.
2. **`organization` → `person`:**
   - Organization-specific fields (`organization_name`, `tax_number`) are automatically set to `null`.
3. Canonical `name` is recalculated based on the new type.

## 9. Domain Operations Implementation

### 9.1 Create Operation (`ContactRepository::create`)
1. Validates domain invariants (`validateDomainInvariants`).
2. Normalizes input attributes (`normalizeAttributes`).
3. Computes canonical `name` (`deriveCanonicalName`).
4. Executes inside `DB::transaction()`.
5. Persists model and dispatches `ContactCreated($contact)`.

### 9.2 Update Operation (`ContactRepository::update`)
1. Retrieves target contact or throws `ModelNotFoundException`.
2. Validates domain invariants.
3. Normalizes input attributes (PATCH semantics: omitted attributes are retained).
4. Handles type transition cleanup if `type` changed.
5. Recalculates canonical `name` if identity fields were supplied.
6. Executes inside `DB::transaction()`.
7. Captures `$dirty = $contact->getDirty()`.
8. Updates record; if `$dirty !== []`, dispatches `ContactUpdated($updated, $dirty)`. If no attributes changed (no-op), event dispatch is skipped.

### 9.3 Delete Operation (`ContactRepository::delete`)
1. Retrieves target contact or throws `ModelNotFoundException`.
2. Captures `$contactId` and `$snapshot` array.
3. Executes inside `DB::transaction()`.
4. Deletes record and dispatches `ContactDeleted($contactId, $snapshot)`.

### 9.4 Query Helpers
- `findActive(array $columns = ['*'])`: retrieves active contacts (`is_active = true`).
- `findByType(string $type, array $columns = ['*'])`: retrieves contacts by type (`person` or `organization`).
